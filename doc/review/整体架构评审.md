# Agent1 × Weizhi 整体架构评审

> 评审范围:`agent1`(本仓库,含 `agent_core` / `java_agent` / `android_agent`)与 `weizhi`(微智,`./sync-weizhi.sh` 拉取的独立仓库),以及二者的集成面。
> 配套文档:[问题与改进建议.md](./问题与改进建议.md)。评审日期:2026-10。

---

## 1. 系统定位与总体形态

Agent1 与 Weizhi 构成一个 **双进程内嵌的端侧智能体系统**:

- **Agent1(`java-agent-core`)**:生产力 **编排层**。负责多轮 ReAct 循环、Session/Run 数据面、工作区 Java 工具、能力检索(`find_caps`)、Coach 运行时钩子、JSONL 审计。约 1.5 万行 Java,宣称 ~3MB 量级,目标是嵌进 Android App / 车机 / 工控平板。
- **Weizhi(微智)**:**执行层**。嵌入式 QuickJS(C + JNI,约 6300 行 C/C++)+ 沙箱文件系统 + 可选 Caps(OS 能力)+ `:agent-tools` 模块(grep/glob/zip/白名单 bash、Skill、MCP 客户端、WebView 执行)。
- **边界原则**(文档明确):Weizhi 的 `android.*` Caps **只**在 QuickJS 脚本内可用,不逐个注册为 LLM 的 Java `@Tool`,避免提示词与权限面失控。

**核心设计取向值得肯定**:「LLM 面少而精 + 细节靠检索」(JS-first 编排)是对「工具膨胀导致提示词爆炸」这一行业痛点的有效回应。两个项目职责分界清晰,没有明显的重复造轮子——除了一个例外(见 §6.3 双沙箱)。

```
┌─────────────────────────────────────────────────────────────┐
│ 宿主(Android App / 桌面 CLI)                                │
│  ProductivityAgentGateway(Android) / ProductivityCli(桌面)   │
├─────────────────────────────────────────────────────────────┤
│ agent1: ProductivityAgentHost                                │
│  Session/Run 编排 · 系统提示词 · 工具注册 · 事件桥            │
├──────────────────────────┬──────────────────────────────────┤
│ agent1: AgentRuntime     │ events.jsonl / runs / transcript  │
│  ReAct loop · 限额 · 溢出 │ (JSONL 审计数据面)                │
├──────────────────────────┤                                   │
│ agent1: LlmClient        │                                   │
│  OkHttp SSE(OpenAI 兼容)│                                   │
├──────────────────────────┴──────────────────────────────────┤
│ weizhi-bridge: ScriptEngineFactory / WeizhiScriptEngine       │
│  $tools 桥(AgentToolsScriptBridge)· $mcp 桥 · JNI Bootstrap │
├─────────────────────────────────────────────────────────────┤
│ weizhi: WeizhiEngine(JNI) → QuickJS(C)                     │
│  沙箱 fs · fetch(allowlist)· native plugins · mcp.connect   │
│  agent-tools: grep/glob/zip/bash 白名单 · Skill · WebView   │
│  Caps: android.* / desktop caps(OS 能力,仅脚本内)         │
└─────────────────────────────────────────────────────────────┘
```

## 2. agent1 内部架构

### 2.1 agent_core(编排内核)

包结构(约 15,200 行 Java,64 个测试类):

| 包 | 职责 | 关键类 |
|---|---|---|
| `core` | ReAct 循环、状态机 | `AgentRuntime`(576 行)、`AgentState`、`CancellationToken`、`ContextTurnLimiter` |
| `session` | 会话与 Run 编排 | `ProductivityAgentHost`(601 行)、`FileSessionStore`、`SessionSummaryService` |
| `run` | Run 落盘与终态 | `FileRunStore`、`RunRecord`、`RunState` |
| `llm` / `llm.openai` | LLM 抽象与 OpenAI 兼容实现 | `OpenAiCompatibleClient`(513 行,SSE 流式)、`DashScopeSseError` |
| `tool` / `tool.workspace` / `tool.web` / `tool.agent` / `tool.script` | 工具接口与内核工具 | `ReadFileTool`、`WriteFileTool`、`EditFileTool`、`ListDirTool`、`ReadUrlTool`、`CapabilitySearchTool`、`AskUserTool`、`ExecuteScriptTool`(286 行) |
| `workspace` | 工作区沙箱与大结果溢出 | `WorkspaceSandbox`、`ToolResultSpill` |
| `event` / `log` | 事件模型与 JSONL 落盘 | `AgentEvent`、`EventPayloads`、`EventJsonlWriter`、`AgentEventJsonlBridge` |
| `capability` / `catalog` / `catalog.sync` / `promote` / `coach` | 自进化数据面 | `CapabilityIndexStore`(633 行)、`CapabilitySearchView`、`CatalogSyncService`、`ProductivityCoach` |
| `script` | 脚本引擎 SPI 与桥 | `ScriptEngineFactory`、`ScriptToolBridge`、`AgentToolsScriptBridge` |
| `mcp` | MCP 配置与能力索引 | `McpServersFile`、`McpCapabilitySync` |
| `prompt` | 系统提示词 | `ProductivitySystemPromptBuilder` |

**运行链路**(`ProductivityAgentHost.runUserMessage`):

1. 校验无进行中 Run → 生成 `runId` → `RunRecord(RUNNING)` 落盘;
2. 绑定审计上下文(`RunAuditScope`)、订阅 `AgentEventJsonlBridge` 与 Turn 检查点;
3. `AgentRuntime.prompt()` 在单线程 executor 上跑 ReAct 循环:LLM 流式请求 → 工具调用(每个工具 `CompletableFuture` + 按工具启发式超时)→ 结果经 Coach 钩子增强 → 溢出控制(`ToolResultSpill`)→ 上下文窗口裁剪(`ContextTurnLimiter` + `ToolResultTruncator` + `MessageHistoryLimiter`);
4. 每轮 `TURN_END` 做 transcript 增量落盘与 Run 检查点(崩溃可恢复);
5. 终态(`SUCCEEDED/CANCELLED/PAUSED/WAITING_USER/FAILED`)写回 Run 与事件。

**并发模型**:三层线程——运行循环单线程 `executor`、工具执行 `cachedThreadPool`(按工具超时控制)、宿主侧(Android `ProductivityAgentGateway`)再包一层单线程 agent 串行队列。取消通过 `CancellationToken` 协作传播;`run_js` 另起 50ms 轮询 watcher 线程把取消翻译成 `engine.cancel()`。

**事件系统**:双通道(`CopyOnWriteArrayList` 监听器 + RxJava `SerializedSubject`),事件类型含 `AGENT_START/TURN_START/MESSAGE_*/TOOL_EXECUTION_*/USAGE/AGENT_END` 等,统一落到 `events.jsonl`。

### 2.2 java_agent(CLI 与桥)

- `ProductivityCli`(`./agent1`,生产力路径)与 `JavaAgentCli`(经典路径,`run_bash`/`run_python`/skill)两个入口;
- `java_agent/weizhi-bridge`:**关键集成件**,详见 §4;
- `:cli` 测试 9 个类,桥测试 16 个类(含 CDP WebView、catalog、docx 集成测试)。

### 2.3 android_agent(参考宿主)

约 9400 行 Kotlin / 83 文件,单一 `productivity` feature,严格按 `ui.view / ui.viewmodel / logic.business / logic.data` 分层(静态脚本 `check-android-agent-layering.sh` 强制)。要点:

- `ProductivityAgentGateway`(`logic.business`):所有阻塞调用收敛到单线程 agent 队列;`check-android-agent-main-thread.sh` 静态禁止主线程直调;
- `app/src/weizhi/` 源集(条件编译)存放 Weizhi 装配代码(`WeizhiHostLoader`、`WeizhiAndroidScriptEngineFactory`、`WeizhiAgentTools` 于 `logic.business.platform`),`BuildConfig.WEIZHI_INTEGRATED` 标记可用性;
- 权限极简(仅 `INTERNET`),附件通过系统文件选择器导入到 `workspace/imports/`;
- `CrashReporter`/`BootTrace` 位于 `com.agent1.android.llm` 包——在分层规则之外,命名易误解(见问题文档 A-02)。

## 3. weizhi 内部架构

### 3.1 C 核心(执行引擎)

- `src/engine.c`(1109 行):QuickJS 嵌入。超时用 `JS_SetInterruptHandler` + `deadline_ms` 软中断(非信号),取消(`nativeCancel`)同理;`runJs` 的错误通道用 `"!"` 前缀字符串返回——原始但有效地避免了 JNI 异常复杂度;
- `src/node_api.c`(2817 行):QuickJS 缺失的 Node 兼容 API(fs/fetch/process 等内置模块实现);
- `src/plugin_loader.c` + `zip_api.c`:带签名校验与 `min_host_abi` 检查的原生插件机制(`docs/NATIVE_PLUGIN_IDL.md`);
- `jni/weizhi_jni.c`(501 行):`AttachCurrentThread/DetachCurrentThread` 处理回调线程,异步 I/O 通过 `nativeComplete*` 回传。

### 3.2 Java 包装(`java/com/weizhi`)

`WeizhiEngine`(JNI 包装):`setFsRoot`(沙箱根)、`enableFetch`(可选 host 后缀 allowlist)、`enableNativePlugins`、`setHostCall`(`__caps` 同步宿主桥,链式叠加)、`nativeResizeRgba` 等。异步 VFS/HTTP 派发到 Java 线程池(默认 16),完成后回调 C 队列。

### 3.3 Android 侧模块(`weizhi/android`)

- `weizhi`:引擎 AAR(C++ + JNI);
- `agent-tools`:`Tool`/`@Tool` 注解反射 + `ToolSchemaGenerator`,`builtin/` 含白名单 `BashTool`(无 shell、白名单命令、读写分离校验)、grep/glob/zip 等;
- `agent-tools-webview`:`WebViewTask`/`BridgeCodec`(桌面 CDP 复用同一套任务模型);
- `caps`:Android OS 能力(`android.files.*` 等,仅脚本内可达);
- `weizhi-maven-publish.gradle`:`sync-weizhi.sh` 同步到 agent1 后供 `weizhi-prebuilt` 无 NDK 导入。

### 3.4 测试

`tests/test_engine.c`(C 引擎测试)+ `tests/java`(ApiCards/Office/Smoke)+ `scripts/test.sh`(含 ASAN 选项)。C 侧测试与 2800 行 node_api 相比覆盖偏薄(见问题文档 W-06)。

## 4. 集成面(最值得审视的部分)

### 4.1 编译期耦合:源码级拼装

`weizhi-bridge/build.gradle.kts` 直接把 weizhi 仓库的 Java 源码 `srcDir` 进自己的 source set:

```kotlin
srcDir(weizhiRepo.resolve("java"))
srcDir(weizhiRepo.resolve("android/agent-tools/src/main/java"))
srcDir(... generated/webview-jvm-sources)  // 从 agent-tools-webview 拷 3 个类
exclude("**/AgentToolsBundle.java")
```

桌面桥对 weizhi 是 **源码级依赖 + 选择性 exclude**;Android 是 **源码联编或预编译 AAR**。这带来最强的版本一致性,但也意味着:

- **master 即契约**:CI 每次克隆 `fengshihao/weizhi` 的 `--depth 1` HEAD,agent1 侧文档以 commit 号(dd7904c/cb3e889/18d0786)记录最低要求,没有 lockfile,weizhi 上游一改 API,agent1 CI 立刻红;
- exclude/拷贝个别类的做法(WebViewTask 等)是 **隐式 fork**,升级时容易漂移;
- `weizhi-prebuilt` 提供无 NDK 路径,但与源码联编产物的一致性依赖人工维护。

### 4.2 运行期耦合:三层桥

1. **`ScriptEngineFactory` SPI**(agent1 定义):`ExecuteScriptTool` 只依赖 SPI,`WeizhiScriptEngineFactory` 在有 JNI 时返回真引擎、无 JNI 时优雅降级(仅内核工具)——**这是全链路设计最好的部分**,降级路径干净;
2. **`$tools` 桥**:`AgentToolsScriptBridge`(core)把当前 Run 的 Java 工具暴露给脚本,`WeizhiScriptToolInstaller`(bridge)以 `__caps` HostCall 链式挂载;排除 `run_js`(防递归)与 `ask_user`,白名单 `exposedNames` 收口;
3. **`$mcp` 桥**:prelude 注入 `mcp_servers.json` 摘要,脚本内 `globalThis.mcp.connect` 连接,MCP 客户端在 weizhi 引擎内,配置与能力索引在 agent1——配置面与执行面分离,合理。

### 4.3 JNI 加载双轨

`WeizhiEngine` 静态块 `System.loadLibrary("weizhijni")`(依赖 `java.library.path`),agent1 桌面侧另有 `WeizhiJniBootstrap.tryLoad(path)` 显式 `System.load` + 失败返回 false 的降级。两套机制并存,行为一致性依赖 `java.library.path` 恰好配置正确。

### 4.4 数据面约定

- 工作区:Android `filesDir/agent1/sessions/<id>/workspace`,桌面 `AGENT1_AGENT_ROOT`;weizhi `setFsRoot` 指向同一目录,两侧各有 **自己的** WorkspaceSandbox 实现做路径校验(语义相近、实现独立,`com.agent1.javaagent.workspace.WorkspaceSandbox` vs `com.weizhi.agent.sandbox.WorkspaceSandbox`,后者支持 `ReadMount` 只读挂载);
- 目录约定:`workspace/artifacts/`、`.spill/`、`jobs/`(超长 inline 脚本落盘)、`tmp/webview_exec`;
- 审计:agent1 `events.jsonl` + `AgentAuditEvents`(catalog 自装、coach 触发等 P.4 事件)。

## 5. 架构优点(保持)

1. **JS-first 编排 + find_caps**:LLM 提示词恒定、细节按需检索,是对提示词膨胀的系统性解法,方向正确;
2. **降级路径完整**:无 Weizhi → 内核工具仍可用;无 JNI → `tryLoad` false 优雅跳过;Android `WEIZHI_INTEGRATED` 条件源集隔离装配代码;
3. **安全分层意识好**:LLM 只见少量工具;脚本内能力再经 `$tools` 白名单与 Caps 边界;weizhi `BashTool` 白名单 + 无 shell + 读写分离是同类实现里的最佳实践;
4. **审计数据面成体系**:`events.jsonl` 全链路 + Turn 检查点 + Run 终态,崩溃恢复与回放有据可查;
5. **CI 门禁自动化**:PMD/SpotBugs/分层静态检查/主线程检查全部脚本化并与 GitHub Actions 同源;
6. **边界文档化**:职责分界表、版本最低 commit、集成指南都有明文,工程协作成本低。

## 6. 架构级风险(概览,详单见问题文档)

### 6.1 取消与超时的断层

agent1 的工具超时/取消机制止于 `AgentTool.execute()`;一旦进入 `run_js`,内部 `$tools.*` 调用用的是 **新建的、永不取消的** `CancellationToken`(`AgentToolsScriptBridge.call`),且 **不经过** AgentRuntime 的超时、溢出、Coach 与审计事件——事件链在脚本内部断掉,只留 run_js 一个整体事件。取消依赖 QuickJS 软中断,但 JS 线程阻塞在同步 `__caps` JNI 调用内时中断不可达。

### 6.2 主仓-依赖仓的版本治理

源码级拼装 + `--depth 1` HEAD + 无 lockfile + 手抄 commit 号,是「方便但脆弱」的典型。建议引入 pin(如 `WEIZHI_REF` + SHA lockfile)或版本号契约(见问题文档 I-01)。

### 6.3 双沙箱/双 JSON/双工具体系

agent1 与 weizhi 各有一套 WorkspaceSandbox;JSON 处理栈 4 套并存(agent1 用 Jackson,bridge 桌面 CDP 用 Gson,weizhi 用 MiniJson + 手写转义)、工具描述/schema 生成各一套。当前规模可接受,但每个重复都是未来漂移点。

### 6.4 单文件巨型 UI

`ProductivityScreens.kt` 1490 行(整个 app Kotlin 共 8300 行),Compose 重组粒度与可维护性风险集中(问题文档 A-01)。

## 7. 结论

整体架构 **方向正确、边界清晰、工程纪律高于平均水平**。最需要投入的三件事:

1. 把「脚本内工具调用」纳入与外层工具一致的 **超时/取消/审计/溢出** 治理(6.1);
2. 把 weizhi 依赖从「master HEAD 漂移」变成 **可 pin 的版本契约**(6.2);
3. 收敛跨仓重复基础设施的 **语义漂移**(6.3),优先统一路径校验与 JSON 通道。
