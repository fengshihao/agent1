## 🔴 高优先级

### C-01 脚本内 `$tools` 调用绕过全部治理机制

`agent_core/src/main/java/com/agent1/javaagent/script/AgentToolsScriptBridge.java`:

```java
ToolExecutionResult result = tool.execute(toolName, params, new CancellationToken(), NO_UPDATE);
```

问题(多个叠加):
1. **不可取消**:传入的是新建的 `CancellationToken`,与 Run 级取消令牌无关联。`ExecuteScriptTool` 的 cancel watcher 只能调 `engine.cancel()` 触发 QuickJS 软中断;当 JS 线程正阻塞在同步 `__caps` JNI 调用里(例如 `$tools.read_url` 在做 HTTP),中断处理器不可达,取消失效,只能等 OkHttp 自己超时;
2. **无超时**:`AgentRuntime.executeToolCall` 的 `estimateToolTimeoutMs` 工具级超时对脚本内调用完全不生效;
3. **无审计**:脚本内每次 `$tools.*` 调用不产生 `tool_call`/`TOOL_EXECUTION_START/END` 事件,`events.jsonl` 里只剩 `execute_script` 一个整体事件——「全链路审计」在脚本环内部断裂,与自进化数据面的可追溯目标冲突;
4. **无溢出/截断**:`ToolResultSpill` 与 Coach 增强同样被绕过,一个大结果脚本内返回即可撑爆上下文(仅靠外层 execute_script 结果截断兜底)。

**建议**:让 `AgentToolsScriptBridge` 持有当前 Run 的 `CancellationToken` 与 `RunLogContext`,在 `call()` 内:
- 传入真令牌并加超时包装;
- 复用 `AgentRuntime` 的审计/spill 逻辑(可抽一个 `ToolCallRecorder` 供两侧共用);
- 短期最低限度:为 `$tools` 调用补记 `AgentAuditEvents` 事件。

### D-01 weizhi 缺席时测试门禁静默降级,`:cli:test` 与桥测试被整体跳过

`.github/workflows/ci.yml`(java-test job)与 `scripts/ci-local.sh` 同样逻辑:

```bash
if [ -d "${WEIZHI_DIR}" ] && [ -f "${WEIZHI_DIR}/scripts/test.sh" ]; then
  ... weizhi 测试 + e2e ...
else
  echo "skip weizhi: ..."
  ./java_agent/gradlew --no-daemon -p java_agent :core:test   # 只有 core
fi
```

一旦 `sync-weizhi.sh` 失败(网络、上游改名、`WEIZHI_SKIP_SYNC` 被置位),CI **绿色通过** 但 `:cli:test`、`weizhi-bridge` 全部 16 个集成测试、Android 侧相关验证都没跑。「绿了」不代表「测过」。历史上 weizhi master 变更多次导致 agent1 破坏(README 记录 dd7904c/cb3e889/18d0786 三个最低 commit),这条降级路径会掩盖此类破坏。

**建议**:
1. 降级分支也应跑 `./java_agent/gradlew -p java_agent :core:test :cli:test`,bridge 测试用「无 native 时的跳过注解」显式标注(如 `@EnabledIfSystemProperty`),而不是随目录存在性隐式决定;
2. master 分支的 CI 中 `sync-weizhi.sh` 失败应直接 fail,不提供静默降级;
3. e2e 脚本退出码必须传播(`set -euo pipefail` 已有,但注意条件分支吞错)。

### W-01 `BashTool` 输出管道死锁:大输出命令必然超时

`weizhi/android/agent-tools/src/main/java/com/weizhi/agent/tool/builtin/BashTool.java`(`execute` + `readOutput`):

```java
Process proc = pb.start();
boolean finished = proc.waitFor(TIMEOUT_MS, TimeUnit.MILLISECONDS);  // 先等退出
String output = readOutput(proc.getInputStream());                    // 后读输出
```

进程输出超过 OS 管道缓冲(典型 64KB)时管道写满、子进程阻塞在 write,`waitFor` 永远等不到退出 → 每次 `cat 大文件` / `find` 大目录这类高频命令都会白等 10s 后报 timeout,而不是返回截断输出(`MAX_OUTPUT_BYTES=50_000` 的截断设计实际很难生效)。

**建议**:并发读输出或 `ProcessBuilder.redirectOutput(File/_PIPE)`,先起 reader 线程再 `waitFor`;或改用 `pb.redirectOutput()` 到临时文件后截断读取。附带:`proc.destroy()` 建议升级 `destroyForcibly()` 兜底。

### A-01 `ProductivityScreens.kt` 1490 行单文件,占 App Kotlin 总量 18%

`android_agent/app/src/main/java/com/agent1/android/productivity/ui/view/ProductivityScreens.kt`。聊天、会话、模型设置等多个 Screen 堆在一个文件:
- Compose 重组与 Preview 粒度恶化,任何改动都触发整文件级审阅;
- 与项目自己「保持改动最小且聚焦」的纪律相悖;
- 新人上手与 blame 历史都被稀释。

**建议**:按 Screen 拆分(ChatScreen/SessionListScreen/...),无需改架构,纯文件级重构;顺带把 `ChatViewModel`(665 行)中流式事件归并逻辑拆出独立 reducer 类。

### I-01 weizhi 依赖无版本契约:master HEAD 漂移即破坏 CI

集成链路现状:
- `sync-weizhi.sh`:`git clone --depth 1` 上游 master HEAD,**无 lockfile、无 tag、无 SHA pin**;
- `weizhi-bridge/build.gradle.kts`:`srcDir(weizhiRepo.resolve("java"))` 源码级拼装 + `exclude` 个别类;
- 契约只存在于文档注释里的最低 commit 号(dd7904c / cb3e889 / 18d0786),人工维护;
- `weizhi-maven-publish.gradle` 由 sync 脚本每次覆盖拷贝到 `android_agent/`——两边 build 脚本静默漂移。

上游任意一次不兼容重构(改 JNI 签名、改 `agent-tools` 包名)都会让 agent1 的 CI 直接变红,且 `--depth 1` 无法本地 bisect 定位。

**建议**(按投入从低到高):
1. 引入 `weizhi.lock`(记录 pin 的 commit SHA),`sync-weizhi.sh` 默认 checkout lock 的 SHA,升级 lock 走显式 PR——一处小改,消除大部分漂移风险;
2. weizhi 侧发布版本号(`WEIZHI_VERSION` 语义化),agent1 记录最低兼容版本而非 commit 号;
3. 长期:把 bridge 所需的 weizhi Java 类(约 20 个)规约为一个稳定 API 模块(weizhi 已有 maven publish 通道),源码拼装仅保留给 C++ 部分。

## 🟡 中优先级

### C-02 路径穿越校验不解析符号链接(symlink escape)

- `agent_core/.../workspace/WorkspaceSandbox.java` `ensureContainedInWorkspace`:字符串逐段比较(`getName(i)`),`Path.normalize()` 不解析符号链接;
- `weizhi/java/com/weizhi/WeizhiEngine.java` `onVfsAsync`:`root.resolve(relpath).normalize()` + `startsWith(root)`,同样不解析符号链接;
- `weizhi/android/agent-tools/.../sandbox/WorkspaceSandbox.java`:`resolve().normalize() + startsWith`,同模式。

攻击面:模型可先 `write_file` 一个指向 `/` 的 symlink(若通过 bash/zip/imports 引入,或历史会话残留),后续读写在 normalize 后仍「属于」workspace,实际落点在沙箱外。Android 上 `filesDir` 内 symlink 受 app 权限约束,危害有限;桌面 CLI 的 `AGENT1_AGENT_ROOT` 若在用户家目录,可写任意用户文件。

**建议**:写路径用「先 `File.getCanonicalFile()` 或 `toRealPath()`(NOFOLLOW)+ 再比对前缀」,或至少在写入时 `Files.createSymbolicLink` 检测拒绝 symlink 组件;zip 导入与 `workspace/imports/` 环节增加 symlink 扫描(参考 zip-slip,`zip_api.c` 侧同理)。

### C-03 `sessionId` 未做路径校验,`deleteSession` 可删任意目录

`agent_core/.../session/FileSessionStore.java`:`sessionDir(sessionId)` = `sessionsRoot().resolve(sessionId)`,无字符白名单。`deleteSession("../../foo")` 会 `deleteRecursive` agentRoot 之外的目录。当前调用方(UI / Host)传 UUID,风险为纵深防御级别;但 `WorkspaceToolProvider`/工具层未来一旦把 sessionId 暴露给模型(如 `list_sessions` 已返回 id),配合 C-02 就是可利用链。

**建议**:`requireSession` 校验 `sessionId` 匹配 `^[a-f0-9-]{36}$`(或至少 `!contains("..")` 且不含路径分隔符),`sessionDir` 一处收口。

### C-04 每次工具调用新建线程池线程,超时后工具线程不回收

`agent_core/.../core/AgentRuntime.java`:
- `toolExecutor = Executors.newCachedThreadPool()` 无上限:每个工具调用一个新线程;
- 超时路径 `toolTask.cancel(true)` 只中断线程,不保证工具内部响应中断(OkHttp/阻塞 IO 不理会);
- 长会话 + 慢工具(网络挂起)会累积线程。

**建议**:bounded pool(`newFixedThreadPool` 或 `ThreadPoolExecutor` + 有界队列 + `CallerRunsPolicy`);`ExecuteScriptTool` 已有 cancel watcher 模式,可推广为「工具声明可中断能力」接口。

### C-05 LLM 重试期间流式增量向 UI 重复发送

`agent_core/.../llm/openai/OpenAiCompatibleClient.java` `streamChat`:第一次尝试若在流中途失败(HTTP 200 后连接断),已 emit 的 text/reasoning delta 已通过 `LlmStreamListener` 推给 UI;`shouldRetry` 命中后第二次尝试再次从头发 delta。UI 层 `MESSAGE_UPDATE` 事件会看到同一段内容两遍(`AgentState.streamMessage` 是覆盖式,最终态正确,但增量消费者如 Android Compose 追加式渲染会重复)。

**建议**:重试前通过 listener 发一个 `reset` 语义(新增 `onRetryAttempt()` 回调,UI 清空当前流式缓冲);或把 delta 缓冲到第一次成功 chunk 后再转发。

### C-06 流式中断时线程自旋风险(`streamOnce` 轮询)

`OpenAiCompatibleClient.streamOnce`:`while (!done.await(100ms))` 每次循环检查取消——功能正确,但 100ms 轮询时长乘以长生成(分钟级)产生数百次无谓唤醒;且 `[DONE]` 到达后 `eventSource.cancel()` 与 `onClosed` 双路径 `countDown` 有竞态无害但值得注意。属可读性/微效率问题。

**建议**:保留现状可接受;若重构,用 `CompletableFuture` 串联 SSE 回调与等待。

### B-01 `estimateToolTimeoutMs` 的 `"read"` case 已过时

`AgentRuntime.estimateToolTimeoutMs`:`case "read" -> Math.min(fallback, 10_000L)`。生产力路径工具名是 `read_file`(`ReadFileTool.name()`),经典 CLI 才叫 `read`。同一 switch 同时服务两条路径的工具名集合,且无测试锁定该映射——超时表和实际注册工具已经出现漂移。

**建议**:把「工具名 → 超时策略」移到 `AgentTool` 接口(`default long suggestedTimeoutMs()`),由工具自声明,消灭字符串 switch 的双路径漂移。

### B-02 每次调用 `execute_script` 新建整个 QuickJS 引擎 + 16 线程池

`weizhi-bridge/.../WeizhiScriptEngineFactory.java` `open()` → `new WeizhiScriptEngine` → `new WeizhiEngine(...)` → `Executors.newFixedThreadPool(16)`(默认 `DEFAULT_MAX_ASYNC_IO=16`)+ 新 QuickJS runtime + 重新 `nativeInstallJavaAsyncVfs`。`ExecuteScriptTool` 每次 `try (ScriptEngine engine = engineFactory.open(...))` 用完即 close:
- Android 上每次脚本调用是「初始化 JNI 引擎 + 起线程池 + 销毁」的重复开销,`execute_script` 恰是主路径最高频工具;
- `$mcp` 客户端缓存挂在引擎实例上(`clients[server]`),引擎不复用 → MCP 连接每脚本每服务器新建一次。

**建议**:engine 池化(session 级单例 + `setFsRoot` 切换 workspace,或至少复用 `ExecutorService`);MCP 客户端缓存上移到 factory/bridge 层。注意池化后 `nativeCancel` 与多 Run 并发隔离的语义要重新设计(当前「一次 runJs」模型是天然互斥,池化需保证同一 engine 同时只跑一个脚本)。

### B-03 桌面 `WeizhiJniBootstrap` 与 `WeizhiEngine` 静态块双轨加载

`WeizhiEngine` 静态块 `System.loadLibrary("weizhijni")` 依赖 `java.library.path`;agent1 桌面用 `WeizhiJniBootstrap.tryLoad(path)` 主动 `System.load` + false 降级。若先 `tryLoad` 失败、后某处类加载触发静态块,会抛 `UnsatisfiedLinkError` 而非走降级路径。当前顺序恰好保证先 bootstrap 再碰 `WeizhiEngine`,但这是隐性时序契约。

**建议**:统一入口——bridge 内只通过 `WeizhiJniBootstrap.tryLoad()` 成功后才允许 `WeizhiEngine` 类初始化(例如 factory 持有布尔门禁),并把静态块改为显式初始化方法。

### W-02 `WeizhiEngine` 原生句柄泄漏无兜底

`weizhi/java/com/weizhi/WeizhiEngine.java`:`nativeHandle` 是裸 long,泄漏完全依赖调用方 `close()`;没有 `Cleaner`/`finalize` 兜底,崩溃场景(C-04 的线程逃逸、Android 进程内异常路径)会泄漏 QuickJS runtime(每个含 JS heap,默认可能数 MB)。错误通道 `"!"` 前缀字符串也让上层无法区分错误类型。

**建议**:实现 `Cleaner` 注册或 `finalize` 兜底仅作最后防线;`runJs` 失败信息建议结构化(错误码 + 消息),上层 `ScriptFailureFormatter` 可据此分类。

### W-03 fetch 重定向可绕过 host allowlist

`WeizhiEngine.doFetch`:allowlist 只校验初始 URL 的 host,`setInstanceFollowRedirects(true)` 会跟随跨 host 重定向(302 → 内网地址/任意主机)。对 Android 内网环境(`192.168.x.x` 车机局域网)构成实际 SSRF 面。

**建议**:关闭自动重定向,手动逐跳校验 allowlist(可复用 agent1 `ReadUrlTool` 的 `PublicHttpUrl.checkPublic` 语义);与 C-02 一并考虑把「URL/路径安全校验」收敛为一个两侧共享的工具类。

### W-04 JNI 回调线程池任务无队列上限与背压

`WeizhiEngine.onVfsAsync/onFetchAsync` 直接 `executor.execute(...)`;`WeizhiLimits.maxAsyncIo` 决定线程数但不限队列。脚本密集发起 I/O(循环 fetch)会堆积无界队列任务,超时中断后这些任务仍继续执行完毕才结束(`deadline` 只影响 JS 侧)。

**建议**:任务提交前检查 engine 是否已超时/取消;队列使用有界 + 拒绝时立即 `nativeComplete(..., false, "busy")`。

### I-02 跨仓 JSON 处理栈 4 套并存

- agent1:Jackson(`ObjectMapper`);
- weizhi-bridge 桌面 CDP WebView 代码:`gson`(`WebViewExecSupport`、`CdpWebViewRuntime`);
- weizhi 自身:`MiniJson`(手写解析器)+ `WeizhiEngine.quoteJson/headersToJson/escape`(手写转义)。

`MiniJson` 与手写转义是典型的「低依赖」取舍,但 `$tools` dispatch、`__caps` 桥、MCP prelude 注入全走这条链,任何一个转义边角(如 `\u2028`、代理对)出错都会产生难查的 JSON 解析失败。

**建议**:weizhi Java 侧手写 JSON 转义统一收敛到 `MiniJson` 的单一实现并补齐边界测试;agent1 侧维持 Jackson。不必强求跨仓统一,但每仓内应只有一种。

### I-03 双 `WorkspaceSandbox` 语义漂移

`com.agent1.javaagent.workspace.WorkspaceSandbox`(core)与 `com.weizhi.agent.sandbox.WorkspaceSandbox`(agent-tools)同名不同体:weizhi 版支持 `ReadMount` 前缀只读挂载 + `guardsDocsNamespace`;agent1 版把 docs 只读硬编码为 `docs/system|capabilities`。两侧「什么是合法路径」规则各自演化,`$tools` 桥允许脚本通过 agent1 工具访问路径,但 weizhi 原生 grep/glob/bash 走自己的沙箱——同一个逻辑路径在两条通道下可能一个放行一个拒绝。

**建议**:明确「路径规则唯一真源」——把逻辑路径语义(logicalPath/ReadMount)定义为集成契约文档 + 双仓共用的黑盒测试集(同一批恶意路径样本在两侧断言一致),低成本消除漂移。

### D-02 `weizhi-bridge` 测试依赖 native 构建存在,但失败信息不明确

`weizhi-bridge/build.gradle.kts` `tasks.test` 设 `java.library.path=${weizhiRepo}/build`,需要先在 weizhi 仓 `cmake` 构建 `libweizhijni`。CI 中 weizhi `scripts/test.sh` 先行构建保证顺序,但本地开发者直接跑 `:bridge:test` 会得到一堆 `UnsatisfiedLinkError`,且当 `../../../weizhi` 目录不存在时 `weizhiRepo` 落到不存在的默认路径,报错为编译错误而非「先 sync-weizhi」。

**建议**:test 任务前加存在性检查,输出 actionable 提示;或用 JUnit `@EnabledIf` 把 native 依赖测试与纯 JVM 测试分层。

## 🟢 低优先级

### C-07 `ProductivityAgentHost` 7 个构造器望远镜(telescoping constructors)

601 行类里 7 个重载构造器链式转发,新增参数(如 `capabilitySearchPlatform`)时每个都要过一遍。建议改 Builder(`AgentRuntimeConfig` 已有 builder 先例)。

### C-08 `appendMessage` 每条消息重读重写 `meta.json`

`FileSessionStore.appendMessage`:每条消息 read+write+atomic-move `meta.json`(更新 `updatedAt`/自动标题)。对话密集时是 3 次 IO/消息。建议:标题只改一次;`updatedAt` 允许延迟批量落盘。

### C-09 `assertNoRunningMainRun` 每条消息全量扫描 runs 目录

`ProductivityAgentHost.assertNoRunningMainRun` 列出并解析该 session 全部 run JSON。Run 多时是 O(n) IO/消息。建议:内存态维护 runningRunId(`runStore` 写入时同步)即可 O(1)。

### A-02 `com.agent1.android.llm` 包名与内容不符且游离于分层外

`android_agent/app/src/main/java/com/agent1/android/llm/` 下只有 `BootTrace.kt` 与 `CrashReporter.kt`(启动追踪与崩溃报告),与「llm」无关;且位于 productivity feature 分层之外。按项目自身规则(utils 应属层内或纯 common),建议移至 `com.agent1.android.common` 或 feature 内 `logic.business.utils`。

### A-03 `llm/scripted` 测试引擎位于 core 主源集

`agent_core/src/main/java/com/agent1/javaagent/llm/scripted/`(脚本化假 LLM)是测试基础设施,却进 main 源集随 ~3MB 内核发布。建议移 testFixtures 或独立 debug artifact,保内核体积纪律。

### W-05 `WeizhiEngine.parseNumberArray` 等遗留 mock 代码混在生产类

`onNativeEnsure/onNativeCall`(`echo_math`/`bad_sig`/`too_new`)是 mock catalog 实现,与真实 plugin loader(`enableNativePlugins`)并存于同一个类,`parseNumberArray` 的手写解析仅在 mock 用。建议拆 `NativeMockHost` 独立类,生产路径类保持干净。

### W-06 C 侧测试覆盖偏薄

`tests/test_engine.c` 单文件对照 2800 行 `node_api.c`;`plugin_loader.c`(586 行,含签名校验安全逻辑)缺少针对恶意 manifest/损坏 zip 的模糊测试。建议:优先给 plugin loader 与 VFS 路径规范补 adversarial 测试。

### D-03 根目录脚本头部中文注释与 shell 便携性

`sync-weizhi.sh` 等脚本按 `bash` 语法(`[[`)但以 `#!/usr/bin/env bash` 调用,总体规范;个别脚本(如 `pick_target` 的路径推断)依赖 `../weizhi` 同级目录这一隐式约定,建议统一由环境变量显式化(已有 `WEIZHI_DIR`,逐步去隐式)。

## 改进路线图建议

**第一步(消除高风险,均为局部改动)**

| 项 | 动作 | 对应问题 |
|---|---|---|
| 1 | `$tools` 桥传入真 CancellationToken + 补审计事件 | C-01 |
