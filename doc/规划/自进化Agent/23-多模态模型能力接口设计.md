# 23 — 多模态模型能力接口设计

> 背景：Agent1 已有媒体文件工具（`media_probe` / 抽帧 / 缩放）与搜图链路，但 **LLM 消息仍是纯文本**；用户选了 DeepSeek Flash 等支持视觉的模型后，agent **看不到**附件图片。文生图、ASR、视频生成等亦未接入 ReAct 环。  
> 承接：[MULTIMEDIA-M0-M1](../../集成/MULTIMEDIA-M0-M1.md)、[20-Office §7 遗留项](./20-Office排版升级与视觉素材管线.md)、[17-能力检索](./17-能力检索-capability-search.md)。  
> 状态：**设计讨论稿**（2026-10-24）。先对齐接口分层，再分 PR 实现。

---

## 0. 结论（推荐拍板）

**不要把「大模型能力」一律做成 LLM `@Tool`。** 业界与本仓库架构都指向 **混合分层**：

| 能力类型 | 推荐形态 | 为何 |
|----------|----------|------|
| **看懂**图 / 截图 / 抽帧 JPEG（理解） | **主对话 content parts**（宿主模型多模态） | Claude Code / Cursor / Codex / DeepSeek Flash 同款：像素进当前 turn，零额外 tool 回合 |
| **ASR / TTS / 文生图 / 图生视频 / 文生视频**（生成与专项） | **Weizhi Package + `find_caps`**，经 `run_js` 调用 | 与 AGENTS「能力一律 Package」一致；不污染 LLM tool schema；可按厂商换后端 |
| **探测 / 抽帧 / 缩放 / 抽音轨**（文件侧） | 现有 `$tools.media_*`（多数不进 LLM schema） | 已实现；与「模型理解」解耦 |
| **文本-only 宿主的兜底** | 可选薄工具 `describe_media`（VL 子调用 → 返回文字） | 仅当当前模型无 vision 时启用；有 vision 时禁用 |

一句话：**理解走主模型消息；专项模型走能力包；文件工具只管路径与字节。**

## 1. 现状差距

| 层 | 现状 | 缺口 |
|----|------|------|
| `AgentMessage` | 单一 `String content` | 无 image / audio part |
| `OpenAiCompatibleClient` | `content` 恒为 string | 无 `image_url` / content 数组 |
| 附件（Android） | `imports/` + 用户文末路径后缀 | 模型只「读到路径名」 |
| 模型目录 | provider + modelId | **无** modalities / vision 能力位 |
| 媒体 | `media_*`、weizhi:image/video/audio | 文件操作，不是 VL |
| ASR | `AliyunDashScopeAsrClient` 已存在 | **未**挂成 agent 能力 / Package |
| 生成式后端 | doc20 明确延期 | 无统一「模型服务」接口 |

## 2. 业界怎么做（对照）

### 2.1 Claude Code

- **理解**：用户粘贴 / 拖拽图片 → 作为消息 content；`Read` 读到图片文件时把像素交给宿主 Claude（多模态）。
- **没有**「vision_tool」之类常驻工具；看图不是 function call。
- Computer use / 截屏是另一条控制面；截出来的图仍回到 **同一多模态上下文**。

### 2.2 Cursor Agent

- 附件与 read 路径上的图 → 缩放后注入多模态上下文。
- 文生图等有独立通知 / 生成路径（轻量 **专项工具**），与「看懂」分离。

### 2.3 Codex CLI

- 附件 + 专用 `view_image`（偏 **B：强制看图工具**）。
- 仍是「理解」路径；生成不混在同一工具里。

### 2.4 OpenAI Agents / Responses

- 理解：`input_image` / content parts（**A**）。
- 生成：内置 `ImageGenerationTool` 等（**B**）。
- 复杂场景用 handoff / `as_tool` 编排专项 agent（**B+编排**）。

### 2.5 DeepSeek Flash / Qwen-VL（API）

- 同一 chat/completions：`content: [{ type: "text", text }, { type: "image_url", image_url: { url: "data:..." } }]`。
- **配置对了模型 id 还不够**：客户端必须发 content parts；Agent1 今天不会发。

### 2.6 模式归纳

| 代号 | 模式 | 适用 |
|------|------|------|
| **A** | 主对话 content parts | 看懂图/页 |
| **B** | 专项模型 `@Tool` | 生图 / ASR / 视频；或强制 view |
| **C** | Package / MCP + 检索 | 可选、可换厂商、不占 schema |
| **D** | 混合 | **业界默认**；Agent1 应选 D，且 **B 尽量经 C 暴露** |

## 3. Agent1 推荐架构（D）

```
用户附件 / media_extract_frame 产物
        │
        ▼
  workspace 相对路径（审计不变）
        │
        ├─►【车道 A】若当前模型 supportsVision
        │     MediaPartInjector：读文件 → 缩放/限大小 → content parts
        │     → OpenAiCompatibleClient 发 multimodal messages
        │
        └─►【车道 C】专项能力
              find_caps("语音转写|文生图|图生视频")
              → weizhi:asr / weizhi:image_gen / …
              → run_js 内调用 ModelBackend（宿主注入的 $model 或包内 HTTP）
              → 结果写回 workspace 路径，文本摘要进对话
```

**刻意不做的事**

- 不为每种模型注册 `deepseek_vision` / `qwen_vl` / `openai_tts` 一堆常驻 `@Tool`。
- 不把 FFmpeg 式 `media_*` 改造成「调用大模型」。
- 不把 computer-use 与 vision 绑成第二个产品；截图理解复用车道 A。

## 4. 接口设计（核心）

### 4.1 消息：ContentPart（车道 A）

保持 `getContent()` 兼容（纯文本拼接 / 会话摘要用），新增可选 parts：

```java
/** 多模态内容块；序列化到 OpenAI 兼容 content 数组。 */
public sealed interface ContentPart {
    record Text(String text) implements ContentPart {}
    /** workspace 相对路径；发送前由客户端转 data URL 或厂商 URL。 */
    record ImageRef(String workspacePath, String mimeType) implements ContentPart {}
    // 远期：AudioRef / VideoRef — 多数 coding API 仍只吃图；先不实现
}

public final class AgentMessage {
    // 现有 String content 保留 = parts 中 Text 的拼接视图，或显式文本
    List<ContentPart> getContentParts(); // 空则回退 content 字符串
}
```

`OpenAiCompatibleClient.toOpenAiMessages`：

- `supportsVision == false` → 只发 string（现状）。
- `supportsVision == true` 且存在 `ImageRef` → `content` 为数组；读盘失败则降级为文本路径提示。

**注入策略（对齐 Claude/Cursor）**

1. 用户本 turn 附件列表（已在 `imports/`）。
2. 可选：本 turn `media_extract_frame` / `media_resize` 新写出的 JPEG/PNG（coach 或 host 策略决定是否自动注入，避免历史爆炸）。
3. 预算：单图 maxEdge（如 1568）、单 turn 最多 N 张、历史中旧图丢弃或改回路径占位。

### 4.2 模型能力位（配置层）

```java
public final class ModelCapabilities {
    public final boolean vision;      // 可收 image parts
    public final boolean toolCalling; // 已隐含为 true
    // 不在此声明 asr/imageGen：那些是 Package 后端能力，不是宿主 chat 模型属性
}

// ModelCatalog / Provider 解析：
// deepseek-flash, *-vl*, gpt-4o, qwen-vl-* → vision=true
// 未知模型默认 vision=false（安全降级）
```

UI（Android / `./agent1 models`）可展示「支持看图」；**选了 Flash 不等于已注入**，还需客户端发 parts。

### 4.3 专项模型后端（车道 C）——统一窄接口

面向 Weizhi / 宿主桥，**不是** LLM function schema：

```java
/** 宿主注入给脚本的「模型专项服务」；实现可换 DashScope / 本地 / 第三方。 */
public interface GenerativeModelGateway {
    /** 语音 → 文本；input 为 workspace 路径。 */
    TranscriptionResult transcribe(TranscriptionRequest req) throws Exception;

    /** 文生图；输出写 workspace，返回相对路径。 */
    ImageGenResult generateImage(ImageGenRequest req) throws Exception;

    /** 文生/图生视频；长任务可返回 jobId + 轮询。 */
    VideoGenResult generateVideo(VideoGenRequest req) throws Exception;
}
```

脚本侧（示意，包名待定）：

```javascript
import { transcribe } from "weizhi:asr";
import { generateImage } from "weizhi:image_gen";

const { text } = await transcribe({ path: "imports/voice.m4a" });
const { path } = await generateImage({ prompt: "扁平插画，蓝白", output: "out/hero.png" });
```

包内实现：

- **优先**调宿主 `$model.transcribe` / `$model.generateImage`（密钥不出脚本、统一限流与审计）；
- 或包内 HTTPS（需 egress 白名单），与现有 MCP/`$mcp` 同类风险面。

`find_caps` 卡片：`kind=weizhi_package`，`entry` 给 5～10 行样例；**不**进 `ProductivityLlmToolSurface` 常驻列表。

### 4.4 可选兜底工具 `describe_media`（薄 B）

仅当 `!supportsVision` 时注册：

```text
describe_media({ path, question? }) → 内部用配置的 VL 模型一次性 chat → 返回纯文本
```

有 vision 的宿主 **不注册**，避免模型「绕一圈看图」浪费 token。

### 4.5 ASR 与已有客户端

`AliyunDashScopeAsrClient` 已实现 WebSocket 会话。落地时：

1. UI 麦克风路径可继续直连（产品交互）。
2. Agent 编排路径：`GenerativeModelGateway.transcribe` → 包装该客户端；再由 `weizhi:asr` 暴露。
3. **不要**再做一个永远出现在 tool list 里的 `asr_transcribe`，除非产品强依赖「模型主动决定转写」且不愿走 `find_caps`（与当前生产力哲学冲突）。

## 5. 与现有分层的关系

| 已有组件 | 关系 |
|----------|------|
| `media_*` / weizhi:image\|video\|audio | **输入准备**：抽帧、抽音轨给 A/C 用；本身不是模型 |
| `image_search` / `images_download` | **检索素材**；与文生图互补（doc20） |
| `find_caps` / Package registry | **专项能力发现与分发** |
| `ProductivityLlmToolSurface` | media 工具继续桥接-only；专项模型也不进 schema |
| JSONL 事件 | A：可记 `media_parts_injected`（路径+字节/张数）；C：记 package 调用与输出路径；**勿**把整段 base64 写入 events |

## 6. 分阶段落地（建议 PR 切片）

| 阶段 | 内容 | 验收 |
|------|------|------|
| **P0** | `ModelCapabilities.vision` + catalog 标注；文档与 UI 提示 | Flash 显示「可看图」，行为仍旧（未注入） |
| **P1** | `ContentPart` + client 序列化 + 附件自动注入 + 预算 | 用户贴图问「图里有什么」→ Flash 能答；纯文本模型无回归 |
| **P2** | `GenerativeModelGateway` + `weizhi:asr` 接 DashScope ASR | `find_caps` 命中；`run_js` 转写 `imports/*.m4a` |
| **P3** | `weizhi:image_gen`（一家后端即可，如通义万相 / 可配置） | 生图落盘 + 可插入 Office 管线 |
| **P4** | 视频生成（异步 job）+ 可选 `describe_media` | 长任务可取消；文本宿主可兜底看图 |

每阶段独立 PR；P1 改 `agent_core` 消息/客户端，**必须**带 JUnit。

## 7. 反模式（明确拒绝）

1. **「一个 `call_model` 万能工具」**：参数里塞 modality/provider —— schema 难、路由糊、难测。  
2. **每种厂商一个常驻 tool**：`dashscope_asr`、`openai_image`… —— 与 find_caps 哲学对着干。  
3. **只靠换模型 id、不改消息格式**：Flash 配好了仍看不见图。  
4. **把生成结果 base64 塞进对话**：应写 workspace，对话只留路径与短摘要。  
5. **在 `logic.data` / 随意 utils 里散落 VL 调用**：遵循 Android 分层；核心序列化在 `agent_core` llm 包。
